# 服务端设计（可选增强方案）

> 主交付形态不变：**纯静态、双击 `index.html` 即用**。本文是"如果上后端"的设计稿，供评审参考，
> 不要求现在实现；落地时也不改判题、统计与现有页面结构（视图仍只调 `js/core/`）。

> **实现状态（2026-10-18）**：`server/` 下已落一个**最小实现**，本文其余部分仍是设计稿。
>
> **已实现**：静态托管；`GET /api/health`（`{ok,version,db}`）；`POST /api/feedback`（字段校验、kind 白名单、限流 10 次/分钟/IP、请求体 ≤64KB）；`GET /api/feedback?status=&bank=&kind=`（需登录，最多 500 条）；`POST /api/feedback/:id/handle`（handled / ignored + `admin_audit`）；`GET /api/export.csv`；`POST /admin/login`（令牌取自 `server/data/admin-token.txt`，5 次/分钟/IP，会话 2 小时 + `recall_admin` Cookie，HttpOnly + SameSite=Lax）；`server/admin.html`（令牌登录、按题库 / 类型 / 状态筛选、标记、导出）；SQLite 库 `server/data/recall.db`（WAL，`PORT` / `DB_PATH` 可改）。冒烟：`node server\smoke.mjs` → `SMOKE PASS 23/23`。
>
> **仍为设计**：轮次跨设备同步（`rounds`）、维护日志下发（`changelog`）、批量上报（`POST /api/feedback/batch`）、`client_id` 幂等、题库版本对账、`PATCH /api/feedback/:id`、cursor 分页、`ADMIN_PASSWORD_HASH` / 多管理员、列表 ETag 与 5 秒缓存、Nginx / systemd / 备份脚本。
>
> **与下文数值的出入（以实现为准）**：请求体 64KB（下文 32KB）；登录限流按 IP 5 次/分钟（下文 5 次/15 分钟 + 用户名）；库名 `recall.db`（下文 `quiz.db`）；鉴权是单令牌文件（下文 scrypt 口令）；处理接口 `POST /api/feedback/:id/handle`（下文 `PATCH`）；错误体 `{ok:false,error}`（下文 `{error:{code,message}}`）；`/api/health` 无 `bankVersions`；`feedback` 表字段与下文不同（无 `client_id`，`question_id` 为 INTEGER，`picked` / `answer` 存逗号分隔串）。

## 1. 定位与边界

- **默认模式：纯静态**。所有能力（作答、判题、进度、轮次、反馈箱、主题）都靠 localStorage，功能完整、离线可用。
- **可选模式：服务端**。前端启动时探测 `GET /api/health`（1.2s 超时）：可用则启用在线能力，超时/失败则静默退回本地模式，**不弹任何提示**。
- 在线能力只有三项：反馈上报与状态回写、轮次（练习记录）跨设备同步、维护日志由服务端下发。（已实现只有第一项中的「提交入库」；轮次同步与维护日志仍是设计。）
- **两种模式功能一致、数据不互斥**：联网不会删除本地数据；同一条反馈/轮次允许"先本地、后上报"。
- 前端改动最小：只多一个 `js/core/api.js`（探测 + 上报 + 队列重试），视图层不感知。题库、判分、统计仍全部来自静态文件与 `createModel()`。（实际实现只有探测 + 单条上报；批量补报的队列重试未做。）

## 2. 数据模型（SQLite）【部分实现】

> 实际只有 `feedback`（字段见文首差异）与 `admin_audit` 两张表；`rounds` / `admin_user` / `changelog` 未建。

**题库不入库**：`js/data/*.js` 是 `ref/题库/*.md` 的生成物（`tools/convert-banks.mjs` 产出），只读、只有 339 题、`file://` 下也必须能跑；
入库会制造第二份真源（改题要同时改 md 和库）、需要迁移脚本、还要为只读数据付查询成本。
改为**静态文件 + 内容 hash 版本号**：生成器把 `version` 写进 `window.*_BANK`，前端与 `/api/health` 的题库版本对账，不一致就提示「题库已更新，刷新一下」。

```sql
CREATE TABLE feedback (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  client_id TEXT NOT NULL UNIQUE,              -- 前端生成的 uuid：幂等 + 去重
  bank_key TEXT NOT NULL, question_id TEXT NOT NULL,
  kind TEXT NOT NULL CHECK (kind IN ('stem','option','answer','explain','other')),
  note TEXT NOT NULL DEFAULT '' CHECK (length(note) <= 200),
  picked_json TEXT NOT NULL DEFAULT '[]',      -- 我的选择 ["B"]
  answer_snapshot TEXT NOT NULL DEFAULT '[]',  -- 提交时的正确答案，日后核对用
  page TEXT NOT NULL CHECK (page IN ('quiz','result')),
  created_at TEXT NOT NULL,                    -- ISO8601 UTC
  status TEXT NOT NULL DEFAULT 'pending' CHECK (status IN ('pending','handled','ignored')),
  handled_at TEXT, handler TEXT
);
CREATE INDEX idx_fb_status ON feedback(status, created_at DESC);
CREATE INDEX idx_fb_question ON feedback(bank_key, question_id);

CREATE TABLE rounds (                          -- 跨设备同步「练习记录」
  id TEXT PRIMARY KEY,                         -- 与前端快照 id 一致：r<ts>-<rand>
  user_token TEXT NOT NULL,                    -- 匿名设备标识（cookie 里的随机串）
  bank_key TEXT NOT NULL,
  scope_json TEXT NOT NULL DEFAULT 'null',     -- {"type":"chapters","chapterNos":[2],"n":0}
  question_ids_json TEXT NOT NULL, answers_json TEXT NOT NULL, stats_json TEXT NOT NULL,
  started_at TEXT, finished_at TEXT NOT NULL,
  source_round_id TEXT,                        -- 重练轮指向原轮
  synced_at TEXT NOT NULL
);
CREATE INDEX idx_rounds_user ON rounds(user_token, finished_at DESC);

CREATE TABLE admin_user (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  username TEXT NOT NULL UNIQUE,
  pass_hash TEXT NOT NULL,                     -- scrypt$N$r$p$salt$hash（node:crypto，不存明文）
  created_at TEXT NOT NULL
);

CREATE TABLE audit_log (                       -- 管理操作留痕
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  at TEXT NOT NULL, actor TEXT NOT NULL,
  action TEXT NOT NULL,                        -- admin.login / feedback.handle / changelog.publish
  target TEXT, detail_json TEXT NOT NULL DEFAULT '{}'
);

CREATE TABLE changelog (                       -- 与 js/data/changelog.js 同结构
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  date TEXT NOT NULL, type TEXT NOT NULL, title TEXT NOT NULL, body TEXT NOT NULL,
  published INTEGER NOT NULL DEFAULT 1
);
```

## 3. 接口设计【部分实现】

> 已实现 health、feedback 的 POST / GET、handle、export.csv、admin/login；`batch`、`changelog`、`rounds` 三行仍是设计。

约定：`Content-Type: application/json; charset=utf-8`；时间 ISO8601 UTC；响应带 `X-Request-Id`；
错误体 `{"error":{"code":"validation_failed","message":"kind 不合法"}}`。

| 方法 | 路径 | 鉴权 | 说明 |
| --- | --- | --- | --- |
| GET | `/api/health` | 无 | `{ok,version,bankVersions:{java,web},time}`，前端探测用 |
| POST | `/api/feedback` | 无（限流） | 单条上报，`client_id` 幂等，重复提交返回同一条 |
| POST | `/api/feedback/batch` | 无（限流） | 本地反馈箱批量上报，≤100 条，逐条幂等，返回 `{accepted,duplicated,rejected}` |
| GET | `/api/feedback?status=pending&bank=web&kind=answer&limit=50&cursor=` | 管理会话 | 列表，`cursor` 分页，返回 `{items,total,nextCursor}` |
| PATCH | `/api/feedback/:id` | 管理会话 | `{status:'handled'\|'ignored'}`，写 `handled_at`/`handler` 与 `audit_log` |
| GET | `/api/changelog` | 无 | 维护日志（`published=1`，日期倒序），`ETag` + 304 |
| GET/POST | `/api/rounds` | user_token | 可选：拉取/上传轮次，`id` 幂等，按 `finished_at` 取新 |

请求示例（`POST /api/feedback`）：

```json
{ "client_id":"8f1c…","bank_key":"web","question_id":"W80","kind":"answer",
  "note":"B 和题干对不上","picked_json":["B"],"answer_snapshot":["B"],
  "page":"result","created_at":"2026-10-17T14:02:11Z" }
→ 201 { "id":42, "status":"pending", "duplicated":false }
```

鉴权：`POST /api/admin/login` 交口令 → 服务端 `scrypt` 校验 → 下发 `sid`（HttpOnly + Secure + SameSite=Strict，8 小时）；所有 `/api/feedback` 读改与 `/admin/*` 都校验会话，写操作落 `audit_log`；`/api/rounds` 只认 `user_token` cookie（匿名，不是账号体系）。

错误码：`400 bad_request`（JSON 坏了）、`401 unauthorized`（无/过期会话）、`403 forbidden`、`404 not_found`、
`409 conflict`（`client_id` 与内容不一致）、`413 payload_too_large`（>32KB）、`422 validation_failed`（字段不合法）、
`429 rate_limited`（带 `Retry-After`）、`500 internal`。

## 4. 后台管理（`/admin`）【已实现最小集】

> 实际实现：单管理员令牌文件登录；题库 / 类型 / 状态筛选；标记已处理 / 忽略；导出 CSV。维护日志编辑未做。

- 口令登录（单管理员，口令取自环境变量 `ADMIN_PASSWORD_HASH`，首次部署用脚本生成哈希）。
- 反馈列表：按题库 / 类型 / 状态筛选，按时间倒序，分页；每行显示定位信息（题库、题号、类型、题干摘要、我的选择、当前答案、备注、时间）。
- 操作：标记「已处理 / 忽略」（写 `audit_log`）、`?format=csv` 导出当前筛选结果（UTF-8 BOM，Excel 直接打开不乱码）。
- 维护日志编辑：后台写入 `changelog` 表并发布（线上优先读表，读不到回退 `js/data/changelog.js`），改完前端下次请求即生效。

## 5. 缓存与并发【部分实现】

> 已实现仅静态资源的 ETag 与 css/js 的 `max-age=3600`；反馈列表直接查库（无缓存），SQLite 只开了 WAL + `synchronous=NORMAL`（无 `busy_timeout`，写操作未包事务）。

- 静态资源：文件名带内容 hash 的（`/assets/*`）`Cache-Control: public, max-age=31536000, immutable`；
  `js/data/*.js` 用 `Cache-Control: no-cache` + 强 `ETag`（内容 hash），未变即 304。
- `GET /api/feedback`：`ETag`（按 `count+max(id)+status 摘要` 生成）+ 5 秒内存短缓存，管理端轮询不至于打满库。
- `GET /api/changelog`：`max-age=60` + ETag。
- SQLite：`PRAGMA journal_mode=WAL; synchronous=NORMAL; busy_timeout=5000;`；写操作全部走事务（`BEGIN IMMEDIATE`）。
- 并发定位：**单进程 + SQLite 串行写**——读可并发、写排队；本场景写入量级是"几十条反馈/天 + 每次交卷一条轮次"，瓶颈在单写者（理论上限数百写/秒，远高于需求），真到瓶颈再上 `PostgreSQL`，接口不变。

## 6. 限流与防滥用【已实现，数值以代码为准】

| 对象 | 规则 |
| --- | --- |
| `POST /api/feedback` | 每 IP 10 次/分钟（固定窗口，内存 Map，单进程够用） |
| `POST /api/feedback/batch` | 每 IP 3 次/分钟，单次 ≤100 条 |
| 管理端登录 | 每 IP+用户名 5 次/15 分钟，失败写日志 |
| 请求体 | ≤32KB；`note` ≤200 字、`question_id` 必须存在于对应题库 |
| 去重（可选） | 同 `bank_key+question_id+kind` 且 10 分钟内已存在 → 记为 `409`，不再入库 |

## 7. 部署【仍为设计】

> 实际只在本机用 `node server\server.mjs` 启动（本机 Node v24.18.0 实测；`node:sqlite` 为内置模块，零依赖）；Nginx / systemd / 备份脚本仍是设计。

```bash
node server/server.mjs            # 零依赖：Node ≥ 22.5 内置 node:sqlite 与 node:crypto
PORT=8080 DB=./data/quiz.db ADMIN_PASSWORD_HASH=... node server/server.mjs
```

- 目录：`server/{server.mjs,db.mjs,routes.mjs,schema.sql,admin.html}`；静态站点仍由 Nginx 直出，`/api` 反代到本进程。
- systemd：`[Service] ExecStart=/usr/bin/node /srv/quiz/server/server.mjs` + `EnvironmentFile=/etc/quiz.env`、`Restart=always`、`User=quiz`；或 `pm2 start server/server.mjs --name quiz-api`。
- Nginx：`location / { root /srv/quiz; try_files $uri $uri/ /index.html; gzip on; gzip_types text/css application/javascript; brotli on; }`
  `location /api/ { proxy_pass http://127.0.0.1:8080; proxy_set_header X-Forwarded-For $remote_addr; }`（限流按 `X-Forwarded-For` 取真实 IP）。
- 备份：每天 `sqlite3 data/quiz.db ".backup /backup/quiz-$(date +%F).db"`（WAL 下可热备），保留 14 天；反馈导出 CSV 每周留档。恢复 = 停进程 → 换文件 → 起进程。

## 8. 迁移路径（本地 → 在线）【仍为设计】

1. 前端探测到 `/api/health` 可用 → 把 `quiz:feedback` 里 `status='pending'` 的条目批量 `POST /api/feedback/batch`。
2. 服务端按 `client_id` 幂等：已存在则跳过并标 `duplicated`；成功后才在前端把本地条目标成 `已上报`（**失败保持 pending，下次再试，不丢数据**）。
3. 轮次同步是可选的：`POST /api/rounds` 上传快照，`GET /api/rounds` 拉取其他设备的记录；冲突按 `finished_at` 取新，快照本身只读、不合并。
4. 断网/服务端挂掉：前端退回本地模式，一切照常；恢复后队列自动补报。

## 9. 本期不做

用户注册/登录体系、多租户与权限分级、实时推送（WebSocket）、题目在线编辑与富文本编辑器、
图片/附件上传与对象存储、全文搜索与错题推荐算法、多语言、前端离线 Service Worker、数据库读写分离。
以上任一项都超出「题库纠错 + 练习记录同步」的范围，先不做，避免范围膨胀。
